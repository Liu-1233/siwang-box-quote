## 2. 为什么会出现 0.2.17 与 0.2.18 并存

**结论：0.2.17 是"源码版本"，0.2.18 是"发布构建版本"，两者代码内容一致。**

时间线（可核对文件与工具脚本）：

1. P1-D-05 系列验收通过的源码包（`siwang-box-p1d05-fix01a-20261122.zip`）内
   `package.json` 始终是 **0.2.17**，本轮交付包继承同一份源码，因此仍是 0.2.17。
2. 正式发布时，构建脚本 `Release-0.2.18-20261122/tools/P1D05REL-build.py` 在**构建根副本**里
   把版本号改为 `NEW_VERSION = '0.2.18'`，理由写在脚本注释里：
   > 版本 0.2.17 → 0.2.18（内容变更 + 更新器按版本号判定，必须递增）
3. 该脚本只改 `build/pack-root/package.json`（临时构建根），**不回写源码树**，
   所以 `resources/app/package.json` = 0.2.18，而源码 ZIP 仍是 0.2.17。
4. `pack.js` 把构建根 `package.json` 原样打进 `resources/app`，生产即为 0.2.18；
   生产的 `app/`、`main.js` 等业务文件与 fix01a **逐字节一致**（发布验收已核对）。

| 对比 | 结论 |
|---|---|
| 生产代码 vs fix01a 代码 | 相同（仅 package.json 版本字段不同） |
| 生产 0.2.18 vs 源码 0.2.17 | 同一套代码的两个"标签" |
| 本轮是否应改版本 | **否**（任务书要求：不擅自升级，先提交核查） |

## 3. 潜在风险（供评审决策）

| 风险 | 说明 |
|---|---|
| R1 版本语义分裂 | 后续任何"按源码 package.json 判断版本"的脚本都会得到 0.2.17，而用户看到的是 0.2.18 |
| R2 发布链依赖构建脚本 | 0.2.18 只存在于构建根；若某次构建漏跑 `P1D05REL-build.py`，会发布成 0.2.17 |
| R3 更新器判定 | `electron-updater` 以 `version` 比较，若源码版本长期停在 0.2.17，后续发布必须每次靠构建脚本 bump |
